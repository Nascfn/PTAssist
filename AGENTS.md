# AGENTS.md

Context for AI coding agents working in this repo. Read this file fully before making changes. Then read the README of the service you are touching (`frontend/README.md`, `backend/README.md`, or `ai/README.md`).

## 1. What this project is

PTAssist is an AI-augmented remote physical therapy platform, built by a 7-person UCF Senior Design team (Group A19) from Fall 2026 to Spring 2027.

- A **therapist** links a patient and assigns a plan of home exercises.
- The **patient** records a video of an exercise and uploads it.
- The system runs **pose estimation**, counts reps, scores form, and writes feedback.
- The therapist reviews results and progress on a **dashboard**.

**Current scope: proof of concept**, due Fri Nov 20, 2026.

- Web app only, for patients and therapists.
- Upload only (no live video).
- 5 exercises (chosen by the AI team in Sprint 1; see `docs/` once they are picked).
- Synthetic and open-source data only.

**Stretch goals (Spring 2027, not now):** live in-session feedback, a mobile patient app, a message queue for analysis jobs. Do not build these unless your task says so, but do not make choices that would block them.

The repo is at the scaffold stage: folders and docs only, no application code yet. Each service gets its skeleton during Sprint 1 (Sep 28 to Oct 11, 2026). If a command, file, or folder described here does not exist yet, it is probably part of an open task. Check Jira before creating it.

## 3. Architecture (settled)

These decisions are final. **Do not change them, add alternatives, or introduce new services, frameworks, or cloud products without asking the human first.**

| Area | Decision |
| --- | --- |
| Frontend | React SPA: Vite, TypeScript, Mantine, React Router, Clerk React SDK, Orval-generated API hooks. One app, patient and therapist sides split by role. Hosted on Azure Static Web Apps |
| Backend API | FastAPI (Python), SQLAlchemy, Alembic. The **only** entry point into the system. Checks the Clerk token, role, and ownership on every request. Uploads go through the API |
| AI service | Separate internal-only Python container. `POST /analyze` takes a session id, exercise, and a temporary video link. Uses OpenCV, ffmpeg, MediaPipe Pose, and rule-based scoring per exercise |
| AI modules | Video-to-keypoints (`ai/app/keypoints/`) and keypoints-to-analysis (`ai/app/analysis/`) are separate. Analysis never touches video, so live feedback can reuse it |
| Handoff | After upload, the API sets the session to `processing`, and a FastAPI background task calls the AI service. The result is stored, and the status becomes `complete` or `failed`. The frontend polls |
| Database | PostgreSQL. AI results in JSONB columns. Schema changes **only** through Alembic migrations |
| Storage | Azure Blob in the cloud, MinIO locally, both behind one storage module in the backend (`backend/app/storage/`). Private buckets, temporary read links |
| Auth and roles | Clerk handles identity only. The role (`patient` or `therapist`) lives in our `User` table. `GET /me` returns it. New users are auto-created as patients; therapists are promoted by the team |
| Hosting | Azure Container Apps (scale to zero) for API and AI service. Images in GitHub Container Registry. Azure resources are set up by hand in the Portal and recorded in `infra/README.md` |
| CI/CD | GitHub Actions. On PRs: lint, tests, image build. On merge to main: build and push images, run migrations as a Container Apps job, deploy. Azure login uses OIDC |
| Local dev | Docker Compose runs Postgres, MinIO, the API, and the AI service |

**Core data model:** `User`, `TherapistPatient`, `Exercise`, `Plan`, `PlanExercise`, `Session`, `SessionResult`. Details in `backend/README.md`.

## 5. Tooling and conventions

**Python (backend and AI):**
- Python 3.12. Dependencies in each service's `requirements.txt` (pip). Pin versions.
- Use a virtual environment (`python -m venv .venv`).
- Lint and format with ruff. Test with pytest.
- Type hints on public functions. Pydantic models for anything crossing a service boundary.

**TypeScript (frontend):**
- npm. ESLint and Prettier. Strict TypeScript.
- Mantine components before custom CSS.
- API calls only through the generated Orval hooks in `src/api/`. If the API changes, regenerate them; do not hand-write fetch calls for existing endpoints.

**General:**
- Keep it simple. Pick the simplest thing that works for the proof of concept.
- Follow the structure in section 4. Do not create new top-level folders.
- Match the style of surrounding code.
- Config comes from environment variables. Add every new variable to the right `.env.example` with a comment.
- If you change how a service works, update that service's README in the same PR.

## 6. Rules you must follow

**Security and data**
- Never commit secrets, API keys, `.env` files, or credentials. Use environment variables.
- Never use or generate real patient data. Only synthetic or open-source data.
- Never commit videos. They live in the team OneDrive. The only exception is a small open-source clip in `ai/tests/fixtures/` whose license allows it.
- Every backend route must check the token, the role, and ownership. A patient sees only their own data; a therapist sees only linked patients.
- Storage stays private. Only `backend/app/storage/` talks to MinIO or Azure Blob, and only through short-lived links.
- Do not log tokens, emails, or other personal data.
- Describe the system as "HIPAA-ready," never "HIPAA compliant."

**Database**
- Change the schema only by adding a new Alembic migration. Never edit a migration that is already merged. Never change the database by hand.

**Git and workflow**
- Never push directly to `main`. Work on a branch and open a pull request. PRs need 1 approving review.
- Name branches after the Jira key, for example `SCRUM-21-clerk-auth`. Put the Jira key in the PR title.
- Keep PRs small and focused on one task.
- Do not commit or push unless the human you are working with tells you to.

**Scope**
- Do only what the task asks. If you spot something else, mention it; don't fix it in the same change.
- Do not add stretch-goal features (live feedback, mobile app, message queue) unless the task says so.
- Do not add dependencies or services beyond the stack in section 3 without asking.

## 7. Finding your task

- Tasks are in Jira: https://ptassist.atlassian.net/jira/software/projects/SCRUM/boards/1 (project key `SCRUM`).
- Each task title starts with a plan ID such as `[S1-BE-4]` (Sprint 1, backend, task 4). Areas: `BE` backend, `AI` AI pipeline, `FE` frontend, `PM` project management.
- Each task description has **Done when** (the acceptance criteria), **Depends on**, and an estimate. Treat "Done when" as the definition of finished.
- Tasks are grouped under epics (for example "Auth and roles") and labeled by team (`backend`, `ai`, `frontend`, `pm`).
- If a task depends on something that isn't done, say so instead of building around it.

## 8. Definition of done

A change is done when:
1. The task's "Done when" condition is met.
2. Lint and tests pass locally and in CI.
3. New behavior has tests (for backend routes, include a wrong-role and a wrong-owner test).
4. Docs are updated if behavior or setup changed.
5. No secrets, videos, or real data are in the diff.

## 9. When in doubt

Ask the human. Especially before you:
- Change anything in section 3.
- Add a dependency, a service, or a cloud resource.
- Touch another team's area (frontend, backend, AI).
- Delete files or change a merged migration.
